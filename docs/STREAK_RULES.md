# Current streak behavior

Verified by `StreakTests` and `StreakConsumerTests`. These describe the existing implementation; they do not establish a new scheduling policy.

- Each COMPLETED check-in contributes one day. A completed day with a freeze still counts once.
- A freeze bridges an absent, FAILED or SKIPPED check-in without adding a completed day. It does not change the check-in status, note, applied XP or refund a failure penalty.
- Repeating a freeze for the same user, habit and date returns the same record without consuming another quota slot. The original request must still be within the allowed today/yesterday window.
- Without a freeze, FAILED breaks the streak. SKIPPED breaks the streak on required days; a recorded rest day bridges it without increasing its count.
- Explicit weekday schedules are supported; without an explicit choice, the default is the first N weekdays starting Monday. A missing or SKIPPED check-in on a resolved rest day preserves the streak. Missing required historical days break it; an absent current day has a one-day grace period.
- Dashboard and streak achievements use the same weekly target. Streak achievements are granted once per account; applying a freeze does not itself run achievement evaluation.
- From migration V41, newly recorded check-ins save a weekly target snapshot; explicit weekdays are also snapshotted. Later habit edits and check-in status/note edits keep these snapshots. Dashboard streaks, streak achievements and the streak used to set a new failure penalty interpret each saved SKIPPED day using its own snapshot. A new check-in uses the recorded schedule for its selected calendar date when known, including backdated entries; dates before recording began retain the current habit schedule fallback.
- Pausing hides the habit from the active dashboard and excludes it from new streak achievement checks. Restoring reuses the saved check-ins and freezes. Restore does not create check-ins, award XP or fill missing days.
- Recorded pause intervals bridge days without a saved check-in and add no completed days. A check-in already saved on a paused date keeps precedence: COMPLETED counts, FAILED breaks unless frozen, and SKIPPED follows its resolved schedule unless frozen. This also applies to corrections made while the habit is paused. Pausing later on the same calendar day cannot erase saved work or hide a saved failure.

## Remaining product decisions

For schedule resolution the current streak calculation prefers a saved check-in's weekday snapshot, then its V41 target snapshot interpreted Monday-first, then recorded state history on or before the selected calendar date, finally the current schedule when history is unknown. A state is eligible only on or after its stored account calendar date, but eligible history is applied in recorded-time order (then ID for an equal instant). A later action replaces the effective state from its own calendar date forward. Therefore, if moving west makes a later observation carry an earlier calendar date, the later action remains authoritative rather than disappearing behind the older date label. Persisted V43 events always have a recording instant; a date/ID fallback exists only for legacy projections and test fixtures missing it. A current target of seven must not override an older resolved rest day. Recorded inactive states bridge unrecorded days only, without overriding saved check-ins or their snapshots. Dates before recording began still have no trustworthy historical schedule and retain the current-schedule fallback; no pause is inferred there. A timezone switch does not recalendar saved check-ins, invent historical states, or fabricate check-ins to bridge gaps. The new-check-in guard already rejects dates recorded as paused; existing entries remain correctable.

## Initial snapshots for new check-ins

- The write path resolves the effective state on or before the selected date from the recorded-time timeline. It copies that state's weekly target and weekdays into the new check-in, excluding later dates and keeping a later action authoritative even when its timezone-derived calendar date moves backwards. Legacy states with no explicit weekdays retain their Monday-first target interpretation.
- If no state exists on or before the date, the new entry snapshots the current habit schedule. This is a fallback for unknown history, not a claim about the original schedule. No events or old snapshots are backfilled.
- Existing entries bypass this initial-snapshot resolution during correction, note edits and retries. Their ID and snapshots, including legacy null snapshots, stay unchanged. The points/failure-accounting snapshots still follow the existing recording-time accounting rules; this change does not infer historical reward amounts.
- Single and batch writes share the upsert path and owner lock. The existing pause guard still rejects new entries in a recorded pause interval and while the habit is currently paused. Saved entries remain correctable.

## Recorded habit state history (V43)

- Creating a habit records a CREATED event with its target and active state. A target or active-state change records a CHANGED event in the same owner-locked transaction as the habit update. Metadata-only edits and retries that leave these two values unchanged create no event.
- For an existing habit with no history, its first actual state change records the previous state as OBSERVED and the new state as CHANGED. Both use the current recording time. Earlier dates remain unknown; migration does not backfill events or label a legacy observation as creation.
- Events retain all same-day transitions, their recording instant, account calendar date and timezone. ID order provides stable pagination even when two events share a clock tick. The current streak implementation uses an effective recorded-time timeline for dates lacking a check-in snapshot; saved check-in snapshots keep precedence. Moving between timezones never rewrites existing event dates or check-ins.
- The owner can read `GET /api/habits/{id}/state-history`, including for a paused habit. Pages contain up to 20 `items` and an optional `nextCursor`; pass it as `beforeId`. Foreign/missing habits return 404 and non-positive cursors return 400. Login is required.
- Single and batch pause/restore operations record history through the same service. Failed operations roll back their history. Personal-data export includes `habit_state_history`; account deletion removes owned events and preserves other accounts' events.
